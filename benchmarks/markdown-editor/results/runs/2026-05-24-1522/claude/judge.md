## Observations

- **Sharp turnaround from the 0758 run**: the same agent on the same task earlier the same day shipped a file that was dead-on-arrival in a browser (a literal `</script>` inside a JS template literal in the seed string closed the outer `<script>` tag — 3/10 functional). This run avoids the issue entirely by leaving the textarea empty and using a `placeholder` attribute instead of seeding content. That single design choice neatly sidesteps the entire `</script>`-in-template-literal hazard class.
- **Recursive blockquote parsing is a quiet win**: `<blockquote>` body is fed back through `renderMarkdown`, so a quote can contain headings, lists, code blocks, even nested quotes — the spec did not require this and most quick implementations do not deliver it.
- **Placeholder design is the cleanest in the comparison**: `\x01C\x01<n>\x02C\x02` (and `…L…` for links) uses ASCII control chars that cannot occur in user text, so the restore pass is unambiguous and can't collide with markdown input. This is a more robust quarantine than space-padded tokens.
- **Mobile layout regression**: `mobile.png` shows the grid still resolving to two 50% columns at narrow viewport, with the unused preview occupying ~50% of the screen. A single `@media (max-width: 600px) { .wrap { grid-template-columns: 1fr; grid-template-rows: 1fr 1fr } }` would fix it; the absence is the only UX gap.
- **`docs/superpowers/plans/2026-05-24-markdown-editor.md` leaks into the deliverable**: planning artifacts from the agent's harness shouldn't ship inside the user-facing output directory. Low severity but worth flagging.
- **Closing fence with a language label is a soft inconsistency**: opener regex is `^\`\`\`\s*([A-Za-z0-9_-]*)\s*$`, closer regex is `^\`\`\`\s*$`. A user who types `\`\`\`js` to open and `\`\`\`js` to close (some habitual users do) would never close the block. README says language labels are consumed-but-ignored on the opener; behavior on the closer is undocumented.
